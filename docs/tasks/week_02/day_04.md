# Неделя 2 · День 4 — Сжатие истории

**Общий день челленджа:** 9.
**Статус:** выполнено по пользовательской приёмке итогового интерактивного сценария.
**Страница:** `/weeks/2/days/4`.
**Итог недели:** дни 6–10 приняты; [сводка и границы подтверждения](../../weeks/week_02.md).

## Оригинальное условие

🔥 **День 9. Управление контекстом: сжатие истории**

**Реализуйте механизм управления контекстом:**

- 👉 храните последние N сообщений “как есть”
- 👉 остальное заменяйте summary (например каждые 10 сообщений)
- 👉 храните summary отдельно и подставляйте его в запрос вместо полной истории

**Проверьте, что потерялось:**

- 👉 проведите диалог на 20–30 сообщений, где по ходу называются конкретные детали (срок, бюджет, ограничение, имя, решение)
- 👉 составьте список этих деталей заранее
- 👉 после сжатия задайте вопросы по каждой детали

**Сравните:**

- 👉 сколько деталей помнит агент без сжатия
- 👉 сколько помнит со сжатием
- 👉 расход токенов до/после

**Результат:**

Агент, который работает с компрессией истории и экономит токены

## Критерии приёмки

Критерии ниже выведены из оригинального условия:

- Последние N сообщений сохраняются без изменений; более ранняя история заменяется summary.
- Summary хранится отдельно и используется вместо полной ранней истории в запросе модели.
- До проверки зафиксированы сценарий на 20–30 сообщений и список проверяемых деталей.
- После сжатия заданы вопросы по каждой детали и оценено число сохранённых деталей.
- Тот же сценарий сравнивается без сжатия и со сжатием; измерены токены до и после.
- Итог показывает фактическую экономию и потери деталей, если они возникли.

## Решение и проверка

Страница /weeks/2/days/4: отдельный постоянный диалог со сжатием и отдельное
сравнение памяти на заранее зафиксированном сценарии. Инструменты не используются.
Личные истории дней 7–8 не читаются и не переписываются. Новых зависимостей нет.

### Память и настройки

agents/compression.py содержит SummaryConversation и построение активного контекста.
JsonHistory поддерживает необязательный класс состояния; по умолчанию прежняя
Conversation, поэтому форматы и поведение дней 6–8 не меняются.

В data/week_02/day_04/conversation.json отдельно хранятся:
- history — полный архив исходных сообщений и output items;
- summary — текст текущей сводки;
- summarized_messages — граница уже сжатых сообщений;
- compression_log — версии сводки, покрытая часть истории и ресурсы операций;
- keep_last / compress_every — настройки, turns — ответы и метрики;
- pending_prompt / last_operation — состояние незавершённой операции.

Файл сохраняется атомарно с блокировкой, как в дне 7, и исключён из Git через data/.
Сводка не вставляется в архив вместо старых сообщений. В модель отправляется
помеченная как данные сводка и ещё не сжатый хвост. Последние сообщения сохраняют
исходное содержимое; служебный status удаляется только из копии для API.
Оpaque reasoning остаётся в архиве, но не считается пользовательским сообщением
и не подмешивается в текстовый контекст этого эксперимента.

Согласованные пользователем настройки по умолчанию: N=6, порог=10 новых
сообщений, которые уже можно убрать из хвоста. Пользователь подтвердил эти
значения; для нового диалога их можно изменить.
В новом диалоге можно выбрать N=2–20 и порог=2–40, только чётные числа:
сообщения считаются как user и assistant, 6 сообщений — 3 пары.
Настройки после начала диалога фиксируются до создания нового.

Перед очередным ответом, если за пределами N накопилось не меньше порога новых
сообщений, они сжимаются. Например, N=6/порог=10: после 16 сообщений, перед
следующим вопросом, первые 10 заменяются сводкой, последние 6 остаются.
Между обновлениями сводки к хвосту добавляются сообщения (для значений по умолчанию
обычно 6–15), ничего не отбрасывается. Уже покрытые сообщения не пересказываются
заново из полного архива: модель получает previous_summary + только новый ранний
фрагмент. Это позволяет наблюдать накопление потерь при повторных сжатиях.

Summary создаётся обычным запросом через общую LLM-границу, не специальным
скрытым API и не локальным алгоритмом извлечения эталонных фактов.
В инструкции требуется сохранить имена, даты, бюджет, ограничения, решения
и уточнения; новых сведений не добавлять. До 2048 выходных токенов и 12000 символов
готовой сводки. Отказ, incomplete, пустая/слишком большая сводка не принимаются:
старые summary и граница остаются, ход останавливается без ответа по плохой памяти.
[Контекст в Responses API](https://developers.openai.com/api/docs/guides/conversation-state).

### Ручная работа

На странице видны текущая сводка, активный контекст, полный архив и ответы.
Таблица ходов показывает:
- вход одного и того же вопроса с полной историей и фактически отправленный вход;
- их разницу (может быть отрицательной, если summary оказалось длиннее);
- usage всего хода и расчётную стоимость, включая создание/обновление summary.

Если summary ещё нет, отдельный повторный подсчёт полного контекста не нужен.
После сжатия полный и сжатый входы считаются с одинаковыми инструкциями и вопросом.
Числа получаются через responses.input_tokens.count, actual usage — из генераций.
Подсчёты являются отдельными сетевыми обращениями и показаны в подробностях.
Стоимость счётчика и индивидуальные наценки провайдера не входят в стандартную оценку.
Неизвестный usage/тариф не подменяется нулём, известная часть стоимости хранится отдельно.

### Фиксированный сценарий проверки деталей

[Сценарий summary-memory-v1](../../scenarios/week_02/day_04.json) содержит
12 пользовательских сообщений и заранее определённые 8 деталей:
проект Север, руководитель Марина, срок 20.12.2026, окончательный бюджет 42000
(вместо предварительных 35000), только локальное хранение, FastAPI, тёмная тема,
отсутствие регистрации. Последние общие сообщения не напоминают эти ответы явно.
Список и допустимые формулировки сохранены до реальных прогонов для дня 10.

Кнопка сравнения выполняет по шагам:
1. 12 настоящих запросов: получается общий диалог на 24 сообщения. Ответы
   ассистента генерирует модель, а не шаблон кода.
2. К полной истории задаются вопросы по всем 8 деталям одним JSON-запросом.
3. Тот же исходный диалог сжимается один раз до summary + последних N сообщений.
4. С теми же инструкциями и тем же проверочным вопросом тестируется сжатая память.

Всего до 15 генераций: 12 общих ответов + полная проверка + сводка + сжатая проверка.
В сравнении сводка принудительно создаётся после готового диалога, не по порогу
ручного чата. Так оба варианта получают один и тот же источник. Результаты полной
проверки не добавляются в исходный разговор и не попадают в сводку, иначе эталонный
ответ мог бы подсказать сжатому варианту решение. Список expected/aliases не отправляется
модели: только исходные сообщения и вопросы без ответов.

Оценка — точное сопоставление нормализованных кратких ответов с допустимыми
формулировками, без модели-судьи. Бюджет проверяется численно. Показаны ответы,
эталоны и результат по каждой детали. Необычный правильный синоним может не пройти:
его следует проверить вручную. Невалидный JSON означает «не оценено», а не 0 деталей.
При разных фактических моделях результат помечается несопоставимым.

Таблица раздельно показывает:
- сколько деталей сохранено из 8;
- вход проверочного вопроса с полной и сжатой памятью;
- расход полной проверки;
- расход сжатой проверки плюс создание summary;
- общие расходы эксперимента, включая создание общего диалога.

Экономия входа не равна экономии суммарных затрат: отдельный вызов summary может
сделать единственную проверку дороже. Выигрыш и сохранение всех деталей не обещаются.

### Хранение эксперимента и границы

Сравнение хранится в data/week_02/day_04/comparison/conversation.json, отдельно
от ручного диалога. Этапы и результаты сохраняются после каждого шага.
Остановка ждёт текущий шаг; продолжение только по кнопке, не после загрузки страницы.
После нормальной остановки этап не повторяется, после аварии с running автоматически
не возобновляется. Новое сравнение архивирует предыдущее, включая незавершённое.
Смена модели или версии сценария требует нового сравнения.

Лимит расчётных расходов фиксирован: $0.50 на ручной ход с summary и ответом,
а также $0.50 на всё сравнение, включая 15 генераций. Перед каждой операцией
вычитаются консервативные резервы предыдущих операций. Это не гарантия полного
биллинга: точный тариф/окно известны в текущем профиле только для gpt-6-luna;
условия расчёта сохранены из дня 8. Нет скрытого изменения модели и повторов.

Вход пользователя до 400000 символов, контекст до 12 млн, JSON до 16 МБ.
Лимиты API/агента сохранены: 30 с на API и 120 с на одну операцию; ответ до 4096
токенов. В сравнении каждый шаг — отдельный HTTP-запрос, поэтому его можно остановить.
Тайм-ауты/ошибки и частичные результаты не объявляются успешной проверкой памяти.
