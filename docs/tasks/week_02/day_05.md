## Оригинальное условие

🔥 **День 10. Управление контекстом: сравнение стратегий**

Реализуйте в агенте **2 стратегии управления контекстом** и переключатель между ними (третья — summary из Дня 9):

- 👉 **Стратегия 1: Sliding Window**

- храните только последние N сообщений
- всё остальное отбрасывайте

- 👉 **Стратегия 2: Sticky Facts / Key-Value Memory**

- введите отдельный блок “facts” (ключ-значение), который хранит важные данные из диалога

(например: цель, ограничения, предпочтения, решения, договорённости)

- обновляйте facts после каждого сообщения пользователя
- в запрос отправляйте: facts + последние N сообщений

**Протестируйте все три стратегии на одном сценарии:**

- 👉 возьмите диалог и список деталей из Дня 9
- 👉 прогоните сценарий на Sliding Window, на Sticky Facts и на summary из Дня 9
- 👉 после каждого прогона задайте вопросы по списку деталей

**Сравните:**

- 👉 сколько деталей помнит агент на каждой стратегии
- 👉 расход токенов
- 👉 сколько кода и вызовов модели требует поддержка каждой стратегии

**Добавьте ветвление диалога:**

- 👉 сохраните checkpoint в диалоге
- 👉 создайте 2 ветки от одного места
- 👉 продолжите диалог в каждой ветке независимо
- 👉 переключайтесь между ветками

**Результат:**

Агент с тремя стратегиями управления контекстом + таблица «стратегия → деталей сохранено / токены / сложность» + вывод, какая стратегия для какого сценария

## Критерии приёмки

Критерии ниже выведены из оригинального условия:

- Доступен переключатель трёх стратегий: Sliding Window, Sticky Facts и summary дня 9.
- Sliding Window отправляет последние N сообщений, отбрасывая остальные.
- Sticky Facts хранит ключи/значения отдельно, обновляет их после каждого сообщения
  пользователя и отправляет facts вместе с последними N сообщениями.
- Все три стратегии проверены на одном диалоге и списке деталей из дня 9.
- После каждого прогона заданы одинаковые вопросы и оценено число сохранённых деталей.
- Сравнены токены, объём кода и число модельных вызовов для поддержки каждой стратегии.
- Из одного checkpoint созданы две независимо продолжаемые ветки с переключением между ними.
- Представлены таблица «стратегия → деталей сохранено / токены / сложность»
  и вывод о подходящих сценариях использования стратегий.

## Решение и проверка

Страница /weeks/2/days/5 содержит ручной диалог с тремя стратегиями, checkpoint,
две ветки от снимка, переключение веток и отдельное сравнение на сценарии дня 9.
Инструменты не предоставляются. Новых зависимостей нет, личные истории дней 7–9
не используются. Пользователь принял результат; прогресс 10 из 35, вторая неделя закрыта.

### Стратегии рабочей памяти

| Стратегия | Что отправляется модели | Поддержка |
| --- | --- | --- |
| Sliding Window | Последние N сообщений и новый вопрос | Нет поддерживающих генераций. После ответа history обрезается до N сообщений. |
| Sticky Facts | Отдельный JSON facts + последние N сообщений + новый вопрос | После каждого сообщения пользователя сначала обновляется facts через модель, затем даётся ответ. |
| Summary | Summary + несжатый хвост + новый вопрос | Используется механизм дня 9: previous_summary + новый ранний фрагмент по порогу. |

N и порог по умолчанию 6/10, как согласовано в дне 9. N — число user/assistant
сообщений, не ходов и не reasoning items. Выбор N=2–20 и порога=2–40, только чётные.
У summary хвост между обновлениями может вырасти сверх N без потери сообщений.
У Window/Facts в рабочей history остаётся только хвост, включая после перезапуска.
Журнал turns хранит просмотр прошлых ходов и расходы, но никогда не читается
для построения контекста. Отброшенные сведения не восстанавливаются из журнала.

Facts — произвольные строковые ключи и значения, не зашитый список эталонов.
Запрос обновления содержит previous_facts, recent_messages и new_user_message.
Модель должна сохранить неизменённые факты, заменить уточнённые, удалить отменённые,
не извлекать новые утверждения из вопросов. После проверки JSON обновлённая память
сохраняется отдельно; затем она используется в ответе. До 50 ключей по 64 символа,
значения до 1000 символов, весь JSON до 20000 символов. Невалидный JSON/отказ/
incomplete не сбрасывает facts в пустой объект: прежняя память остаётся, ход останавливается.
Вызов обновления выполняется и при вопросе без новых фактов, включая финальный recall.

agents/strategies.py содержит построение контекста и валидацию facts.
Модуль дня координирует обновления через общую операцию дня 9, SimpleAgent и TokenMeter.
Для facts общая операция получила необязательную инструкцию, максимум 2048 выходных
токенов. Summary дня 9 не переписан; принятые дни сохраняют своё поведение.

### Переключение стратегии и ветки

Чтобы не уничтожать текущую память, «Применить в новой ветке» создаёт копию
журнала и текущего хвоста в новой ветке с выбранной стратегией/N/порогом.
Старые facts и summary не импортируются в другую стратегию, прежняя ветка остаётся.
Если N увеличен, сообщения сверх ранее доступного хвоста не восстанавливаются.
Это явная смена политики для дальнейшего разговора, без скрытого платного пересчёта прошлого.

agents/branches.py хранит Workspace с ветками и checkpoint. Checkpoint включает
history, facts, summary, границу сжатия, настройки, модель, журнал и метрики.
Его можно создать только после завершённого хода. Действие «Создать ветки A и B»
делает две глубокие копии одного снимка; копируются также вложенные словари и списки.
Новые сообщения и обновления памяти одной ветки не меняют другую и сам checkpoint.
Можно переключаться на любую ветку и продолжать её; незавершённую ветку можно
просмотреть, но её запрос не повторяется автоматически.

Workspace атомарно сохраняется в data/week_02/day_05/conversation.json, через
прежний JsonHistory с блокировкой. AttachedWriter пишет изменение дочерней ветки
вместе с родительским документом, под его блокировкой. Порядок активной ветки,
checkpoint и обеих веток восстанавливается после перезапуска. До 8 веток и
8 checkpoint. Новое рабочее пространство архивирует предыдущее целиком.
Файлы игнорируются Git, API-ключи и заголовки не сохраняются. Маршруты с идентификаторами
работают со словарями Workspace, не используют пользовательские ID как пути файлов.

### Сравнение на одном сценарии

Используется [summary-memory-v1](../../scenarios/week_02/day_04.json) и тот же
список 8 деталей из дня 9, включая изменение бюджета с 35000 до 42000.

1. 12 настоящих ответов модели создают общий исходный диалог на 24 сообщения.
2. Этот неизменный разговор по очереди воспроизводится для трёх рабочих памятей.
   Ответы ассистента берутся из общего реального разговора, а не генерируются
   заново для каждой стратегии: это контролирует различие исходных данных.
3. Window обрезает хвост без вызовов. Facts обновляется после каждого из 12
   пользовательских сообщений. Summary обновляется по порогу дня 9.
4. В конце summary дополнительно сжимается до точно последних N сообщений,
   а facts обновляется перед проверочным вопросом (13-е обновление).
5. Всем трём задаётся одинаковый JSON-вопрос по каждой из 8 деталей.

Эталонные expected/aliases не передаются модели. Проверочные ответы одной
стратегии не добавляются в исходник другой. Полная исходная история в сравнении
хранится отдельно от рабочих памятей; генерация Window/Facts не получает её скрыто.
Для измерения входа без сокращения полный источник дополнительно получает только
endpoint подсчёта токенов, не генерация ответа этой стратегии.

При N=6/порог=10 обычно 30 генераций: 12 общих ответов, 3 проверки,
13 обновлений Facts, 2 summary. При N=2/порог=2 — до 39 (11 summary).
Число шагов и поддерживающих вызовов показано фактически. Обновление Facts и
Summary в одном шаге может включать 2 генерации, остановка ждёт весь текущий шаг.
Лимит $0.50 на весь эксперимент, включая общий диалог; продолжение только явно,
после остановки или перезапуска загрузка страницы не выполняет оплачиваемых действий.
После ошибки/unknown новое сравнение архивирует прежнее, без автоматического повтора.
Смена модели/версии сценария требует нового сравнения.

Состояние сравнения — отдельный JSON data/week_02/day_05/comparison/conversation.json.
Оно не перезаписывает ручные ветки или данные дня 9.

### Таблица и выводы

Для каждой стратегии показаны:
- число сохранённых деталей из 8 и ответы по каждой детали;
- вход проверочного запроса;
- сумма usage/стоимости поддержки этой памяти и проверки;
- фактическое число поддерживающих модельных вызовов;
- число непустых строк выбранных функций реализации.

Общие 12 ответов учитываются один раз в общих расходах, отдельно от стоимости
поддержки трёх стратегий. У Facts учтены все обновления, включая вопрос проверки,
у Summary — оба сжатия по умолчанию. Подсчёты токенов показаны отдельно от генераций.
Неизвестные usage/цены не становятся нулём. Невалидный JSON — «не оценено», не 0 деталей.
Оценка деталей переиспользует алиасы дня 9; необычную правильную формулировку нужно
проверить вручную. Отдельной модели-судьи нет.

Мера объёма кода локальная: complexity() считает непустые строки без комментариев
только в перечисленных функциях, без общей API/хранилища/интерфейса. Список функций
открыт в подробностях. У Facts учтены построение хвоста/JSON, валидация и update_facts;
у Summary — существующие compression_end, active_context и compress дня 9.
Это проверяемая оценка выбранной реализации, не универсальная оценка трудоёмкости.

На странице есть рекомендации по механике: Window для короткого локального
обсуждения, Facts для явных договорённостей, Summary для длинного повествования.
После законченного прогона вывод дополняется наблюдаемым числом сохранённых деталей
и минимальной расчётной стоимостью поддержки/проверки. При разных фактических моделях,
невалидных ответах или неизвестной цене соответствующий рейтинг не рассчитывается.
Единичный сценарий не является общим рейтингом моделей или доказательством экономии.

### Лимиты и проверки

Фиксированный расчётный лимит $0.50 на ручной ход, включая поддержку памяти,
и отдельно $0.50 на всё сравнение. Оценка и проверенный профиль модели из дня 8;
договорные/региональные наценки и возможная цена endpoint подсчёта не включены.
Это не гарантия полного биллинга. Сообщение до 400000 символов, вход до 12 млн,
общий JSON до 16 МБ, 30 с на API и 120 с на операцию, до 4096 токенов ответа
и 2048 для поддерживающих вызовов. Обрезка API выключена, смены модели/fallback нет.

На 2026-11-16: Ruff check/format-check и mypy прошли;
pytest — 213 passed, 1 live skipped; node --test tests/js/*.test.cjs — 55 passed.

и личные файлы предыдущих дней не менялись.

4. Явно запустить сравнение, посмотреть 8 деталей, ресурсы, поддержку и строки кода.
