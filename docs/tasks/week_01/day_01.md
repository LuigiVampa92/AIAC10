## Решение и проверка
В базовом проекте уже есть главная страница `/` с навигацией по всем неделям
и дням, страница первого дня с формой и общая граница вызова OpenAI API.
Модуль дня отправляет запрос через общую LLM-границу. На странице под формой
расположены ответ модели и раскрываемые панели «Запрос к API · JSON» и
«Ответ API · JSON». Запрос содержит фактические model, input и max_output_tokens;
ответ — полный объект, сериализованный SDK, включая доступные status, output и usage.
Это JSON тела, а не побайтовая запись HTTP-трафика. Ключ и HTTP-заголовки
не отображаются. При ошибке показывается тело запроса и безопасное сообщение,
сырые ошибки провайдера не выводятся. Во внутренних offline-проверках явно указано
отсутствие API-обмена; название demo не требуется для работы пользовательского интерфейса.
Данные экранируются и остаются только на странице текущего результата, без истории.

На пользовательской странице показывается только оригинальное условие из этого
документа. Решение, проверки, статус сдачи и инструкции агентам остаются здесь.
Над формой режим и настроенная модель показаны как неизменяемая информация;
под результатом — фактическая модель ответа. Пояснение об оплате из интерфейса убрано.

Форма отправляется без перезагрузки страницы (fetch). Во время ожидания виден
индикатор без процентов; повторная отправка заблокирована, поле ввода и панели
остаются доступными. Результат относится к тексту на момент отправки; его исходный
запрос виден в JSON. Ответ и отладка обновляются на месте, открытые панели сохраняются.
После ошибки кнопку можно использовать снова, автоматического повтора нет.
Без JavaScript работает обычная отправка с перезагрузкой.

Проверки без сети: lint и форматирование Ruff, mypy и 52 теста прошли.
Проверены соответствие отладочного JSON аргументам API, сериализация ответа,
отсутствие ключа в этих данных, экранирование HTML и пустые/demo-состояния.
Дополнительно прошли проверка синтаксиса JS и четыре сценария с подменой DOM/fetch:
успех, ошибка API, разрыв сети, ошибка валидации; проверены ожидание, блокировка
дубликатов и восстановление кнопки. Визуальная проверка через браузерный инструмент
не состоялась: browser access host недоступен. Работу интерфейса проверил пользователь.
Пользователь проверил интерфейс и сообщил об ошибке API. С его разрешения выполнен

Ключ и содержимое `.env` не выводились. Добавлены безопасные сообщения для квоты,

После пополнения баланса пользователь подтвердил, что запросы выполняются.
Это подтверждение реального сценария пользователем, а не успешный API-вызов агента.

## Повторная валидация по запросу

`tests/test_day_01.py` проверяет полный серверный путь первого дня:
форма → registry → модуль дня → API-граница → текст ответа и отладочные JSON.
Offline-тесты используют подмену SDK, проверяют параметры и отсутствие утечек,
а также то, что ошибка провайдера не подменяется demo или успешным ответом.
Они дополняют существующие тесты формы, ограничений ввода и LLM-клиента.

- Без расходов: `.venv/bin/pytest tests/test_day_01.py -m "not live_openai"`.
- По явному запросу на один реальный вызов:
  `.venv/bin/pytest tests/test_day_01.py::test_day_01_live_openai --live-openai -s --tb=short`.

Live-тест использует текущие ключ и модель из штатных настроек, не меняет `.env`,
не требует запущенного сервера и делает один запрос с `max_output_tokens=512`.
Проверяет непустой текст в серверном HTML, JSON фактического запроса, завершённый
ответ API и ID модели. При успехе выводит модель и usage без ключа.
Проверка JS/индикатора и визуального оформления выполняется отдельно в браузере.
Не требовать одинаковой формулировки ответа между запусками.

Последняя проверка при добавлении этих тестов: 54 offline-теста прошли,
1 live-тест пропущен по умолчанию; Ruff, format-check и mypy прошли.
Live-тест в этот раз не запускался; подтверждение успешной реальной работы остаётся

результат и фактическую модель; при ошибке не повторяет платный вызов автоматически.
