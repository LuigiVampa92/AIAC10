# Неделя 1 · День 3

**Статус:** условие получено; реализация и API-эксперименты предстоят.

## Оригинальное условие

🔥 День 3. Разные способы рассуждения

Возьмите 5–10 задач с известным ответом
(логических, алгоритмических или аналитических)

Решите их через API четырьмя способами:

- 👉 получите прямой ответ без дополнительных инструкций
- 👉 добавьте в промпт инструкцию: «решай пошагово»
- 👉 попросите модель сначала составить промпт для решения задачи,
  а затем используйте его
- 👉 создайте в промпте группу экспертов
  (например: аналитик, инженер, критик)
  и получите решение от каждого

Прогоните все четыре способа при двух настройках рассуждения:

- 👉 с минимальным рассуждением (`reasoning.effort: low` / минимальный budget_tokens / отключено)
- 👉 с максимальным рассуждением

Сравните:

- 👉 сколько задач решено верно
- 👉 сколько токенов и времени ушло

Результат:
Таблица «способ × рассуждение → верных ответов / токены / время» + вывод, какие приёмы промптинга перестают что-либо давать, когда рассуждение включено

## Критерии приёмки

Критерии ниже выведены из оригинального условия:

- Подготовлены 5–10 задач с эталонными ответами и явными правилами оценки.
- Один набор задач проверяется всеми четырьмя способами при двух настройках
  рассуждения: всего восемь комбинаций для каждой задачи.
- Для способа с генерацией промпта сохраняются сгенерированный промпт и результат
  его последующего использования; для группы экспертов — решения каждого.
- Учитываются токены и время всех вызовов способа, включая подготовительный вызов.
- Представлена таблица «способ × рассуждение → верных ответов / токены / время»
  и вывод по фактическим результатам о пользе приёмов при включённом рассуждении.

## Решение и проверка

Доступна только общая техническая форма. Набор задач, оценка и эксперименты ещё
не реализованы; API-прогоны не выполнялись. Demo не выполняет условия задания.

Следующий шаг — согласовать набор задач, правила оценки, модель и бюджет.
Минимальную и максимальную настройки определить по поддержке конкретной модели;
фиксировать фактически отправленные параметры, не подменять настройку API текстом промпта.
Для сравнения заранее определить способ измерения времени и суммирования usage,
включая доступные сведения о токенах рассуждения без двойного счёта.

## План для следующего агента (предложение, ещё не реализация)

Контекст уже принятых решений — [handoff.md](../../handoff.md), процедура проверок —
[testing.md](../../testing.md). Оригинал условия выше не менялся. Набор задач,
интерфейс и конкретные API-параметры дня 3 пока не утверждены и не реализованы.

1. Начать с пяти фиксированных задач разных типов и явных эталонов. Подготовить
   задачи/эталоны агентом, не просить пользователя написать их. Предпочесть
   вычислимые ответы с независимой проверкой: арифметика с условиями, строковый
   алгоритм, граф, расписание интервалов, логическая задача. Показать набор и правило
   сравнения; не использовать LLM как судью по умолчанию.
2. Для каждого задания реализовать 4 способа × 2 настройки рассуждения. Предлагаемая
   интерпретация «экспертов»: один запрос с ролями и ответом каждого плюс явный
   итоговый ответ для оценки. Не создавать дополнительные рабочие агенты/фреймворк.
3. Метапромптинг — два последовательных вызова: создание промпта и применение
   полученного промпта. Качество/отказы/обрезание первого этапа должны быть видимы;
   не продолжать с пустым промптом и не подставлять заранее написанный молча.
4. При одном повторе каждой комбинации это 40 решений, но **50 API-вызовов** для
   пяти задач: (1 прямой + 1 пошаговый + 2 метапромпт + 1 эксперты) × 2 × 5.
   Для десяти задач — 80 решений и 100 вызовов. Повторы, отдельные вызовы каждому
   эксперту или дополнительные проверки увеличат этот объём; показать число заранее.
5. Проверить актуальную поддержку reasoning выбранной моделью/API по официальной
   документации до задания параметров. Зафиксировать реальные минимальное и
   максимальное значения; не считать слова «решай пошагово» настройкой reasoning API.
   Не менять глобальный `.env` или модель остальных дней без запроса пользователя.
6. Не переносить автоматически лимит 512 из первых двух дней: при высоком reasoning
   он может уйти на внутренние токены и не оставить полноценного ответа. Выбрать
   явные достаточные пределы входа/выхода и времени для дня 3, проверить малым
   разрешённым пилотом, затем запускать полную серию в согласованном объёме.
7. Правила оценки задать до эксперимента и применять одинаково ко всем способам.
   Для экспертов хранить все решения, но явно выбрать, какой итог сравнивается
   с эталоном. Отказы, неразобранные и неполные ответы не должны исчезать из знаменателя.
8. Суммировать usage и время обоих этапов метапромптинга, сохраняя детали каждого.
   Reasoning-токены, если они уже входят в output/completion tokens, второй раз
   не прибавлять. Недоступные показатели отмечать как неизвестные, а не нулевые.
   Не пытаться извлекать скрытые рассуждения: для оценки нужны конечные ответы
   и доступные API-метрики; пояснения модели можно хранить отдельно.
9. Переиспользовать принятый UX дня 2: последовательные прогоны, прогресс,
   остановка после текущего вызова, частичные результаты/экспорт, сырые JSON и
   время/токены в карточке. Выводы — в документации, без поля «Ваш вывод» в интерфейсе.
   Не копировать целиком специфичную логику JSON Schema/stop из дня 2.
10. Добавить offline-тесты эталонов/оценки, матрицы 4×2, параметров reasoning,
    двух этапов/агрегации и отказов. Повторить общую регрессию дней 1–2 и JS;
    отдельные live-проверки выполнять явно, не включать их в обычный pytest.

До полных платных прогонов нужно определить модель, реальные значения reasoning,
пределы и бюджет. Независимую подготовку набора, формы и тестов можно выполнять
без API. Число задач 5 и один вызов группы экспертов — предлагаемые стартовые
значения для обсуждения, а не дополнительные требования организатора.
