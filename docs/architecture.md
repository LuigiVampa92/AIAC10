# Архитектура

Приложение — локальный модульный монолит: FastAPI + серверные Jinja2-шаблоны.
Интерфейс использует HTML-формы. Для первого дня `static/task.js` отправляет форму
через fetch и обновляет только блок ответа/отладки без навигации. Без JavaScript
сохраняется обычная отправка формы. Во время запроса показан неопределённый progress,
повторная отправка блокируется, остальная страница остаётся доступной.
HTML результата рендерится тем же серверным шаблоном с экранированием данных.
При сетевой ошибке автоматических повторов нет: результат вызова может быть неизвестен.

## Навигация по реализации

- `src/aiac/web/app.py` — главная `/`, страницы дней, обработка форм и `/health`.
- `src/aiac/web/templates/` и `static/` — общий интерфейс и оформление.
- `src/aiac/tasks/registry.py` — перечень 35 дней и загрузка их модулей.
- `src/aiac/tasks/week_XX/day_YY.py` — поведение конкретного дня.
- `src/aiac/llm/client.py` — demo и запросы к OpenAI; `config.py` — настройки.
- `tests/test_web.py` — маршруты, формы и экранирование;
  `tests/test_llm.py` — контракт API и безопасные ошибки с подменой клиента.
- `tests/test_day_01.py` — приёмка первого дня по полному серверному пути;
  один opt-in live-тест через TestClient проверяет реальный API и HTML ответа.
- `tests/conftest.py` — общая блокировка сети в offline-тестах и флаг `--live-openai`.
  Live-маркер без флага пропускается. Команды повторной проверки описаны в README.

Инструменты разработки (Codex, OpenCode и другие) находятся вне приложения.
Выбор инструмента не меняет маршруты, архитектуру или способ авторизации приложения в API.

## Поток запроса и ограничения

Поток: маршрут дня → registry → отдельный модуль day_YY.py → общая LLM-граница.
Страница показывает только раздел «Оригинальное условие» из docs/tasks.
Статус, критерии, решение, проверки и заметки для агентов остаются в том же
Markdown-документе и не выводятся в интерфейс. Отдельной копии условия нет.
Сырой HTML в Markdown отключён.
Ответ модели экранируется, не интерпретируется как HTML.

Общие части: config, web, llm. Логика конкретного задания — только в его модуле;
новые общие компоненты выделяются по необходимости. Нумерация: week_01…07, day_01…05.
Корень определяется по расположению исходников; это checkout-приложение,
не автономный wheel: docs должны оставаться рядом с исходниками.

По умолчанию demo не создаёт OpenAI-клиент и не делает сетевых вызовов.
Реальный режим требует AIAC_LLM_MODE=live, AIAC_LLM_PROVIDER=openai,
OPENAI_API_KEY, AIAC_LLM_MODEL.
Первый день использует Responses API; второй — Chat Completions для всех вариантов
сравнения (включая настоящий stop). Вызовы ограничены timeout 30 секунд и 512 токенами
вывода, без автоматических повторов. Исходный ввод — до 4000 символов;
второй день отдельно ограничивает инструкцию формата (2000) и схему (12000).
Выбор модели — явный, без fallback.
Это ограничения отдельного запроса, не денежная квота. Бюджет задаётся отдельно
в аккаунте провайдера; приложение пока не ведёт учёт расходов.

База данных и история запусков пока не нужны. При появлении экспериментов добавить
хранилище запусков: модель, промпт/версия, параметры, ответ, время, usage,
commit и стоимость при доступности данных. Не сохранять секреты.

Условия дней 2–5 первой недели требуют повторных экспериментов, оценки ответов
и сравнительных таблиц. Во втором дне реализованы серия и экспорт в браузере; текущий
`ModelResult` содержит текст, режим, модель и отладочные JSON тела запроса и объекта
ответа SDK. Перед реализацией экспериментов потребуется
согласовать дальнейшее хранение результатов и расчёт стоимости.
Во втором дне usage и время уже фиксируются для каждого ответа Chat Completions.
Новую БД или зависимости заранее не вводить.

Безопасность: localhost, секреты только через окружение/.env, никакой авторизации
ChatGPT из OpenCode в приложении. До публикации сервера нужны аутентификация,
CSRF-защита, rate limiting и ограничения расходов. Сейчас публичный хостинг запрещён.
OpenCode permissions не являются системной песочницей и не блокируют все обходы shell.

## Первый технический срез (не задание челленджа)
35 страниц, Markdown-описания, отдельные модули дней, форма с demo-ответом,
опциональная OpenAI-интеграция, проверки без сети. Неизвестные задания не реализованы.

## Оформление и темы недель
Шапка содержит название «AI advent Challange №10» и имя участника «Павел Васильев».
Главная объединяет дни в отдельные блоки недель: пять кнопок в ряд на широком экране,
с переносом на узком. Темы недель взяты из публичной программы
[автора челленджа](https://mobiledeveloper.tech/ai_advent_10): Основы LLM, База про агентов,
Оптимизация агента, MCP, RAG, Локальный ИИ, Пайплайн.
Темы служат навигацией и не заменяют оригинальные условия отдельных дней.

На странице первого дня под формой доступны раскрываемые панели отладки API.
JSON запроса формируется из тех же аргументов, которые передаются в Responses API;
JSON ответа сериализуется SDK. Авторизация и заголовки не включаются. Сырые исключения
не показываются; при API-ошибке сохраняется только тело отправляемого запроса.
Отладочные данные экранируются шаблоном, не записываются в файлы и не имеют истории.

Над формой отображаются только информационные режим и настроенная модель из Settings;
редактировать их со страницы нельзя. После вызова результат показывает фактическую
модель из ответа API. Пояснения об оплате остаются в документации.

## Конфигурация и расширение провайдеров

Практическая инструкция по `.env`, переменным и расширению:
[Локальная конфигурация](configuration.md).

Внутренний режим, провайдер и ID модели разделены. Действующая конфигурация:

```dotenv
AIAC_LLM_MODE=live
AIAC_LLM_PROVIDER=openai
AIAC_LLM_MODEL=gpt-6-luna
OPENAI_API_KEY=
# Ключ следующего провайдера добавляется только при его подключении:
# ANTHROPIC_API_KEY=
```

По прямому запросу пользователя локальный `.env` переведён на эту схему с сохранением
ключа и выбранной модели. Старый `AIAC_OPENAI_MODEL` заменён на `AIAC_LLM_MODEL`,
режим `openai` — на `live`. Старые имена/значения не являются совместимыми aliases;
если они заданы в IDE или shell, обновить их и перезапустить сервер.
Внутренний demo остаётся для offline-проверок и не становится отдельным провайдером.
Ключи принадлежат конкретным провайдерам: не использовать один общий ключ для всех
адресов и не отправлять ключ OpenAI другому сервису при смене provider.

`generate()` — общая граница модулей дней; она выбирает провайдера по
`AIAC_LLM_PROVIDER`. Сейчас доступен только адаптер `generate_openai()`.
Неизвестный provider приводит к безопасной ошибке до создания OpenAI-клиента,
без отправки ключа и скрытого fallback. `ModelResult` содержит фактического
провайдера отдельно от режима. Ключ OpenAI читается только внутри его адаптера.

При подключении следующего провайдера выделить адаптер в отдельный модуль,
сохранив общий контракт. Эксперименты второго дня используют `llm/chat.py`:
он фиксирует usage/время и передаёт stop и строгую схему в API без подмен.
Temperature и reasoning остаются задачами следующих дней.
Новые SDK и зависимости согласуются отдельно.

## Эксперименты второго дня

`day_02.py` содержит план, построение пяти вариантов и валидацию JSON/подмножества
JSON Schema. `day_02.html` использует общую оболочку и CSS; `day_02.js` последовательно
вызывает POST `/weeks/1/days/2/plan` (только валидация) и `/weeks/1/days/2/runs`
(не более одного API-вызова на запрос). Web-маршруты только связывают эти части.
Обычный POST дня 2 не выполняет прежний одиночный запрос: нужна форма эксперимента.

План фиксирует настройки на странице, модель/провайдер проверяются сервером при
каждом прогоне. Сервер не хранит серию. JSON-экспорт формируется браузером, без ключей.
Браузер обновляет таблицу и карточки через textContent, без вставки HTML модели.
При несовместимых параметрах повтор варианта пропускается; при квоте/сети серия
останавливается. Результаты и исходы проверяются отдельно от факта завершения серии.
