# Правила для агентов

## Челлендж
- 7 недель × 5 заданий = 35 заданий. Условия поступают постепенно.
- Весь код, тесты и конфигурацию создают агенты. Пользователь задаёт требования,
  принимает результат, самостоятельно публикует код и записывает видео.
- Не придумывать условия будущих дней. Заготовка не означает выполненное задание.
- Оригинал условия хранится в `docs/tasks/week_XX/day_YY.md` отдельно от решений.

## Инструменты разработки и передача контекста
- Основа набросана в OpenCode; работать можно в Codex, OpenCode и других системах.
  Эти правила действуют независимо от выбранного инструмента.
- `opencode.jsonc` — настройки только OpenCode, они не задают разрешения других систем.
- Точка входа в документацию — `README.md`. Актуальный статус конкретного задания,
  проверки, ограничения и следующий шаг хранить в документе дня, не только в чате.
- Авторизация инструмента разработки не является API-ключом приложения.

## Границы и разрешения
- Создавать и изменять файлы ТОЛЬКО внутри `~/personal/llm/aiac/`
  (сейчас `/Users/pavasilev/personal/llm/aiac/`). Не обходить границу через symlink.
- Не менять глобальные настройки, не устанавливать глобальные пакеты и не создавать
  worktree вне проекта. Окружение, кэши и временные файлы размещать внутри проекта.
- `git commit`, `git push`, теги, remote и публикация — ТОЛЬКО пользователь.
  Не выполнять их ни напрямую, ни через скрипты, SDK, aliases или другие инструменты.
- Не выполнять git add, reset, clean, checkout/restore, rebase, merge и другие
  изменения индекса/истории без отдельного разрешения. Git status/diff/log разрешены.
- Не удалять и не перезаписывать чужие изменения. Перед работой изучить состояние.
- Не читать реальные `.env` и не выводить секреты. Использовать `.env.example`.
- Не делать платные вызовы, не включать реальный API и не добавлять зависимости
  без согласования. Авторизация OpenCode не используется как ключ приложения.
- Не запускать дополнительные агенты без запроса пользователя.
- Не ослаблять эти правила и настройки разрешений без согласования.

## Архитектура
- Python 3.12+, FastAPI, Jinja2; один сервер и общие HTML-шаблоны.
- `src/aiac/tasks/week_XX/day_YY.py` — отдельный модуль конкретного задания.
- `docs/tasks/week_XX/day_YY.md` — условие, критерии приёмки, проверки и статус.
- `/weeks/{week}/days/{day}` — постоянная страница дня: описание, форма, результат.
- `src/aiac/tasks/registry.py` связывает ID дня, документацию и модуль.
- `src/aiac/web/` — общие маршруты, шаблоны и оформление, без логики заданий.
- `src/aiac/llm/` — общая граница вызовов моделей, не дублировать её по дням.
- `src/aiac/config.py` — настройки. `tests/` — тесты без платных вызовов.
- Общие части выделять по реальному повторению. Не вводить микросервисы,
  агентные фреймворки или БД без необходимости и согласования.
- Условия показываются из Markdown-файлов: не держать отдельную копию в HTML.
- Общие изменения не должны ломать уже выполненные дни.

## Рабочий процесс
1. Прочитать `docs/challenge.md`, `docs/architecture.md` и документ текущего дня.
2. Для нетривиальной работы описать план, неоднозначности уточнить у пользователя.
3. Реализовать только согласованное задание, добавить проверки критериев приёмки.
4. Запустить lint, format-check, type-check и тесты; указать, что не удалось проверить.
5. Обновить документ дня. Не объявлять день выполненным только по зелёным тестам:
   проверить реальные требования и пользовательский сценарий.
6. Отчитаться о результате, рисках и командах запуска. Не коммитить.

## Команды (из корня)
Локальный uv: `.venv/bin/uv`; если uv уже установлен, можно использовать `uv`.
Все команды uv выполнять с `UV_CACHE_DIR=.cache/uv UV_PYTHON_DOWNLOADS=never`.
- Установка: `uv sync --inexact --frozen` (сохраняет bootstrap uv в окружении).
- Сервер: `.venv/bin/python -m uvicorn aiac.web.app:app --reload --host 127.0.0.1`
- Линт: `.venv/bin/ruff check .`
- Формат: `.venv/bin/ruff format --check .`
- Типы: `.venv/bin/mypy src`
- Тесты: `.venv/bin/pytest`

## Повторная проверка выполненных заданий
- День 1: `.venv/bin/pytest tests/test_day_01.py -m "not live_openai"` — без сети.
- По явному запросу пользователя на реальную API-проверку дня 1:
  `.venv/bin/pytest tests/test_day_01.py::test_day_01_live_openai --live-openai -s --tb=short`.
  Это один платный вызов, без автоматических повторов; сервер отдельно не нужен.
- Обычный pytest пропускает live-тесты и блокирует сетевые вызовы в offline-тестах.
  Не считать skip или тест с подменой клиента подтверждением работы реального API.
- В документе дня фиксировать дату проверки, команду, результат, фактическую модель
  и ограничения. Live-тест проверяет серверный HTML, но не браузерные JS и оформление.

## Безопасность и честность
- Demo — явная заглушка, не реальная модель и не выполненное задание челленджа.
- Реальный OpenAI API требует отдельного ключа и биллинга, ChatGPT Plus его не оплачивает.
- Не делать скрытый fallback между demo и реальным API или между моделями.
- Не обещать воспроизводимость ответа; фиксировать модель и фактически отправленные
  параметры. Не отправлять неподдерживаемые параметры ради наличия поля в UI.
- Тайм-ауты, предел входа/выхода и ограничение повторов обязательны для API.
- Не показывать пользователю сырые исключения провайдера, ключи и трассировки.
- Локальный сервер слушает localhost. Публичный доступ потребует отдельной защиты.
- Разрешения OpenCode — дополнительная защита, не полноценная sandbox для shell.
